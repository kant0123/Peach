# ADR-0134：整库补全把文件名补全队列跑完

- 状态：已采纳
- 日期：2026-11-02
- 相关：`src/peach/web_library_processing.py`、`src/peach/iv_completion.py`、ADR-0133、ADR-0132

## 背景

ADR-0133 把第二趟限定为「全馆处理末尾每趟最多 120 部、900 秒」，用 `attempts.json`
记住试过的行，让每一趟往未试过的行前进。实际使用里仍有缺口：

1. 约 2.2 万部视频的馆藏里有 4,566 部没有任何署名人。用户点「仅补全影片资料」
   （`stage=metadata`）或「补全已入库影片」（`stage=collect`），任务正常结束，但
   这些既有影片没有变化；同一部在详情页「重新采集资料」却能补上。
2. 原因是选取顺序：第二趟按 rank 优先级排，rank 0（番号已定、常规来源全灭）永远
   排在前面；4,566 部里 rank 0 的数量远超 120，rank 1（常规来源给过部分资料）与
   rank 2/3 的行在这两趟里永远轮不到。单部重新采集只排一行，所以总能被轮到。
3. 这两趟本来就是「补存量」的入口，用户在等的是既有影片被补上，而不是「这一趟
   只走 120 部」。

## 决策

用户明确发起的整库补全把文件名补全队列跑完：

- `stage` 为 `metadata`（仅补全影片资料）或 `collect`（补全已入库影片）、没有
  `asset_ids`、不是增量同步时，第二趟不设行数与时间上限（`limit=0`、
  `time_budget=None`），按优先级把本趟算出的整条队列走完。
- 其余入口保留原来的小尾巴：日常「同步新增文件」等增量同步每趟仍是 120 部 / 900 秒；
  单独运行的第二趟仍是 500 部 / 1800 秒（ADR-0133 不变）。
- 整库补全的进度沿用任务卡：当前影片、已处理/队列总数与完成后的 `iv_completion`
  统计都随任务状态返回；暂停与停止在每部之间生效，停止后不再开始下一部。
- 同一组缺口仍在 `attempts.json` 里记 7 天（失败 1 天、认不出 7 天、不适用 30 天），
  队列走完后再跑不会重复问同一批行。

## 后果

- 整库补全会跑上数小时，这是把 4,566 部存量过一遍的实际成本；任务卡可暂停、停止，
  账本里已经写入的结果保留。试过记录在整趟结束时才写进 `attempts.json`，中途被打断的
  那一趟会在下一次重问一批没记下的行（候选与来源快照仍照旧复用，不会重复落库）。
- 常规来源没有给出资料的整行都会轮到第二趟；JavArchive 找不到番号的行照样留原状，
  只记试过记录，不猜番号。
- 「同步新增文件」不替整库补全跑存量：它只发现新增文件，仍用 120 部的小尾巴。
- 候选、自动落库、封面与人物资料仍按既有规则结算，本决策只改这一趟的队列长度。

## 验证

临时账本与模拟来源覆盖：整库 `metadata`/`collect` 请求把 `limit`、`time_budget` 传成
不限；指定影片与增量同步仍取 120 部 / 900 秒；停止后队列不再开始下一部。既有
`tests/test_metadata_iv.py` 的选取、试过记录与第二趟管线用例保持通过。

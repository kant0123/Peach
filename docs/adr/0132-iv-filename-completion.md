# ADR-0132：未取得作品的第二趟文件名补全

- 状态：已采纳
- 日期：2026-10-31
- 相关：`docs/SOURCING.md`「既有未取得条目的文件名补全」、`src/peach/iv_completion.py`

## 背景

常规资料补全按番号走来源链。没有番号的视频不进入来源链；有番号但官方与综合索引全灭的
作品也会停在那里。现有 `identify_resources.py` 只生成联网识别清单，要人或智能体在外侧
填回，不能跟着常规补全自动接上。IV（イメージビデオ）尤其明显：DMM 的 GraphQL 目录只收
PPV，`IMBD-214`、`JSSJ-077` 这类在它上面零结果，r18.dev 只收其中一部分。

发行目录本身常把资料写在名字上：`[佐々木麻衣] FIRST TOUCH`、`[JSSJ-077] 純粋少女`。
这些线索此前只用于文件名展示，没有进入补全。

## 决策

常规补全保持原样，第二趟单独运行。`process_library` 结束时把既没拿到资料、也没拿到
封面的行记进 `iv_pending_ids`；Web 任务与 CLI 在正常处理返回后调用
`peach.iv_completion.complete()`。

第二趟只做两段：

1. `peach.filename_metadata` 从文件名与父目录读番号、标题、出演者。番号缺失时用
   JavArchive 按标题或第一位出演者搜索；标题的包含／高相似与出演者一致同时成立，且
   同一番号只有一件时才采用。有歧义不写任何值。
2. 番号确定后，把该行交给既有 `process_library`，并在该内容类型的链末尾追加
   `javarchive`。候选合并、自动落库、封面尺寸与来源规则全部沿用既有判定；JavArchive
   是转载来源，需要两家一致的字段仍留在复核队列。

番号写入用 `auto:iv-completion-<批次>` 归属，`require_empty=True`，同一批次可整批撤回。
每趟最多 30 部，余下的下一趟常规处理后再拾。

不接 DUGA（JS loading 页，HTTP 503）与 Getchu（年龄确认页）：现有 HTTP 取页到不了正文。
本次取得范围是 JavArchive 的 IV 页与关键词搜索。

## 后果

- 常规链的查询顺序、短路规则与既有测试不变；第二趟只在常规处理结束后发生。
- 没有番号、也没有严格匹配的作品不会被猜一个番号；它们保持原状，不再进入自动队列。
- 有番号且文件名认得出番号的行，JavArchive 作为补空来源可以自动落库；文件名认不出
  番号的行即使第二趟搜到了番号，自动落库仍受 `_group_identifies_code` 约束，通常留在
  复核队列。
- 第二趟按批次限量，避免一次后台任务把整个馆藏重新扫一遍；进度沿用处理任务的状态。
- 新增无外部依赖，不改数据库结构。

## 验证

临时账本与模拟来源覆盖：r18.dev 的 `actors` 出演者、JavArchive 的 IV 资料块与关键词
搜索、文件名末尾／方括号／父目录番号、严格匹配唯一性、第二趟的链覆盖与自动落库调用、
无匹配时不写值。真实网络只做只读试跑，不写账本。
